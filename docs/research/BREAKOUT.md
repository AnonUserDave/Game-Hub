# Atari 2600 Breakout reconstruction

2026-10-13 development checkpoint. This is a native ARM64 development reconstruction of the supplied cartridge. The core contains no processor interpreter, platform compatibility runtime, Wine, or Rosetta. Its pixel contacts are native mathematical geometry reconstructed specifically for this title. Static agreement with cartridge constants and native unit tests does not establish faithful gameplay, visuals, audio, controls, or release readiness. The current test host is the son's M5 Pro MacBook Pro / 24 GB; **M1 performance unverified**.

## Selected source and reproducibility

```sh

  --ghidra /path/to/ghidra_12.1.2_PUBLIC \
  --java /path/to/native/jdk/Contents/Home/bin/java
./Tools/test.sh -XCTest GameHubTests.BreakoutCoreTests
```

The second command uses an existing analysis engine; it never installs one or executes the cartridge. Direct Ghidra 12.1.2 uses `6502:LE:16:default`, the Raw Binary loader, normalized base `$F000`, and `Tools/ExportBreakout.java`. The local project, log, command provenance, and disassembly remain under ignored `Library/Research/breakout2600`. The game uses `BRK` as a compact call to `$F1C6` and resumes at instruction address +2; ordinary control-flow traversal otherwise stops at the first `BRK`. The export script recovers those continuations explicitly and now rejects any unclassified byte. Preparation independently checks each listing byte against the ROM, verifies all direct transfer targets and BRK continuations, and records the coverage receipt: 946 instructions / 1,810 instruction bytes, plus 238 classified data/padding bytes, zero unclassified bytes. The data ranges are `$F0FE..F131`, `$F200..F236`, `$F782..F7FF`, and five BRK padding bytes. Neither the REA shared active target nor another title's analysis project is changed.

Acceptance for this development checkpoint:

- Select/hash the supplied revision and retain address/offset evidence for every recovered gameplay table.

- Exercise source constants and observable transitions through native ARM64 XCTest; inspect the final diff.
- Label remaining reconstruction choices and every missing comparison/acceptance gate.

No dependency, graphics baseline, OS minimum, source archive, or other title is changed by this scoped work. The M1 Air / 8 GB / 2560 × 1600 constraint still applies.

The publisher’s [Breakout instructions](https://atari.com/pages/breakout) describe two walls, the 864 maximum, five balls, timed competition and alternating final team displays. They do not identify this ROM hash or establish frame-level agreement. Their two-wall description conflicts with the selected revision’s explicit timed branch. Native gameplay now follows the selected bytes and records that disagreement; it does not invent a timed second-wall trigger to match the manual.

The complete static byte/direct-target coverage allows the following scoped reconciliation. `$F490..F4A2` requests a scored rebuild only after paddle contact at BCD 432; timed modes explicitly branch past it. The request is applied next frame by `$F132..F1C5`, with collision processing suspended for that frame. Neither a wall-empty predicate nor an 864 terminal branch appears in the fully classified cartridge. Removing the second wall therefore records progress while the ball continues until the shared five-round schedule ends. For two teams, `$F3EB..F3F3` decrements the shared count only on return to team 0. Ended scoreboard displays alternate teams every 256 frames (`$F352..F368`), including a 36-entry rotation plus cleanup frame. Native teams swap atomically while preserving 37 frames of collision suspension; the source’s intermediate wall-rotation pixels are still absent.

The same frame-counter path has a separate 65,536-frame overflow exit to console selection (`$F356..F358 → F3B4`). The native now returns to a distinct `selection` phase at this boundary, before timer increment or fire processing, retains score/rounds and clears motion. The same exit applies to an ended scoreboard. The source’s console-selection HUD and attract animation remain absent; this phase is not a game-completion claim. Original execution comparison is still required for the selected revision/manual discrepancy and all transition graphics.

Preparation also recovers the ten original three-pixel HUD digits, five rows each, with the kernel’s reversed row order. Both 50-byte nibble-oriented tables agree after their different playfield bit orders. The glyphs exist only in ignored `Library/Imported/breakout2600/media.json`. `BreakoutMedia.load` fences source identity and bounds its read to 16 KiB. The source HUD shows three BCD digits (the timer display is the internal counter modulo 1000), plus remaining-round/team digits. Exact color and monochrome register values are exposed by the core from `$F7AA..F7BD`; RGB/NTSC calibration remains unverified.

## Verification and limits

The first-party preparation command verified the current archive and ROM hashes and decoded all listed tables. Direct Ghidra static disassembly completed successfully. `BreakoutCore.swift` typechecked with the native ARM64 Swift 6.3.1 toolchain and macOS SDK.

The revised Ghidra export independently completed its complete-byte assertion. These are M5 development receipts, not comparison with a running original cartridge.

The tests cover authored arithmetic and ordering: integer raster origin, previous-display contact timing, selected brick mismatch at a visible edge, paddle response before current input, no positional clamps, fractional catch/serve bytes, ascent-only steering history, timed no-rebuild behavior, scored deferred rebuild, continued flight after 864, shared rounds, split sample phase, ended team comparison, source frame-overflow selection versus normal scoreboard completion, source audio/visibility phase, source color codes, bounded original-HUD loading, deterministic saved contact replay and invalid-save rejection.
